# Observability: usage and error records, player IDs, alerts and a runbook

## What was built

The hosted playmat at `tcgreplay.app` now records what players do, and what
goes wrong, as structured records that never identify a player.

- **Pseudonymous player IDs.** Each player is named by a stable ID (`p_` and
  16 hex characters). It is a keyed, one-way hash of their email address,
  under a new required secret, `TCGREPLAY_PLAYER_ID_KEY` (at least 32
  characters, read only from the environment). Hosted mode refuses to start
  without the key. The start-up line says "player IDs on" and never shows the
  key. The same account keeps the same ID across sign-ins, assistants,
  restarts and redeploys. Without the key, an ID cannot be matched to an
  email.
- **One JSON record per line on standard output**, read in DigitalOcean
  Insights. The fields come in a fixed order (`time`, `level`, `event`,
  `player`, `tool`, `action`, `assistant`, `message`, `reason`, `idle`) and
  the events form a closed list of 14: `sign_in`, `sign_in_refused`,
  `sign_out`, `player_day`, `tool_call`, `import`, `new_game`, `error`,
  `limited`, `game_expired`, `account_removed`, `board_refused`,
  `admin_refused`, `admin_action`.
- **Usage.** A new MCP middleware runs inside the rate limit and sees every
  tool call:
  - it writes `tool_call` with the tool and the assistant;
  - it adds `import` and `new_game` when those tools succeed;
  - it writes `error` with a redacted message when a call fails.

  A player's first activity in each UTC day writes `player_day`, so a day's
  count of `player_day` records is its number of distinct players. A failed
  board action writes `error` naming the action, through a new board error
  hook.
- **Existing log lines switched to the ID.** Every log line that used to
  carry an email address is now a record keyed by player ID:
  - sign-in, refused sign-in and sign-out;
  - the rate limit and the user cap;
  - game expiry and account removal;
  - a foreign board link, and admin refusals.

  The admin page's own card-set and image log lines name the admin by ID. A
  guard test parses the hosted packages' sources and fails if a logger call
  formats an `.Email`.
- **Redaction.** Error messages are the one place a player's own text could
  reach a record. Before an error message is written, its quoted parts become
  `"…"`. Any run of words that also appears in the call's arguments, or in
  the current game's player names, card names, battle log or decklists,
  becomes `…`. The playmat's own wording is kept.
- **Admin lookup.** The admin page (`/admin`, admins only) has a "Find a
  player's ID" form. It POSTs an email and shows that player's ID. The
  address never appears in a URL or a record.
- **Alerts and runbook.** `.do/app.yaml` declares the new secret and three
  alert rules: a restart, CPU above 80% for 10 minutes, and memory above 80%
  for 10 minutes. A new runbook, `docs/observability.md`, covers:
  - the record format and the event catalogue;
  - what is never recorded, and how redaction works;
  - how player IDs work;
  - the Insights searches for each daily number;
  - the path from a player's email to their errors;
  - the graphs and the alerts;
  - capacity, and retention.
- **Memory measurement.** `TestMemoryPerGame` (`internal/game`) runs only
  with `TCGREPLAY_MEASURE_MEMORY=1`. It reports the heap one full imported
  game with branches adds, and how many such games fit in 512 MiB and 1 GiB
  at 70% use.

## Why it matters

Once TCG Replay is public, the maintainer needs to know how much it is used
and to spot problems before players report them. Each day's distinct
players, tool calls by assistant, imports, new games and errors can now be
read in DigitalOcean alone. When a player reports a problem, the admin
lookup leads straight from their email to their error records. The records
never hold an email, a name, a token, a battle log, a decklist or card data,
so the privacy page can describe exactly what is kept.

## Deviations from the plan

- **The person tasks are deferred to the maintainer.** "Set up the secret and
  alert recipients, deploy and measure" and "Apply the launch limits" were
  closed as accepted shortfalls. So was the measurement criterion of
  "Record capacity and retention, and set the launch limits". The launch
  limits stay at 10 players on `apps-s-1vcpu-0.5gb`. The runbook records
  capacity as pending, with the measurement steps.
- **Retention is provisional.** DigitalOcean documents no retention for
  Insights logs or metrics; it documents only alert history, at 30 days. The
  runbook therefore gives 7 days for usage records, error records and
  platform metrics, marked "to be confirmed by the maintainer".
- **The secret must be set first.** `TCGREPLAY_PLAYER_ID_KEY` has to be set
  on the live app before this work reaches main. Hosted mode will not start
  without it, and every push to main deploys.
- **Middleware order.** The tool-call middleware is added in the same
  `AddReceivingMiddleware` call as the rate limiter. go-sdk v1.6.0 wraps a
  later call outside earlier ones.
- **Redaction keeps common words at the edges.** Common playmat words at
  either end of a redacted run stay visible, and so do numbers.
- **The admin page shows player IDs.** Its "checked by" and "cleared by"
  lines now show the admin's player ID, not their email.
- **The measurement lives in `internal/game`**, as `measure_memory_test.go`.
  It uses the mirror corpus log with the corpus deck as the opponent's list.
- **Pre-existing flaky tests**, unrelated to this work:
  `internal/usergames` `TestWaitingDoesNotKeepGame` (under `-race`) and
  `internal/mcpserver` `TestInstructionsTeachTheLoop` (a TempDir cleanup
  race).
