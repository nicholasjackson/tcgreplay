# A TCG Replay sign-in page, with username and password accounts for directory reviewers

## What was built

The hosted playmat now has its own sign-in page. Whenever an assistant connects TCG Replay, or a browser that is not signed in opens the board, the browser lands on TCG Replay's sign-in page instead of jumping straight to Google. The page is in the Studio look (the TCG Replay mark, the shared design tokens, light interface), loads nothing from other sites, and cannot be framed or cached. "Sign in with Google" is its first and most prominent action, and choosing it works exactly as before: the same account, the same games, the assistant's connection completes, and the board opens signed in. Sign-ins made before the release still work.

When the operator sets `TCGREPLAY_PASSWORD_ACCOUNTS` (an encrypted hosted setting of `username:bcrypt-hash` entries, as `htpasswd -nBC 12 <username>` prints them), the page also shows a username and password form, with a note that it is for reviewer and invited accounts. These accounts:

- sign in exactly as Google accounts do, through one shared completion: the assistant connects and its tools run as that account, the same browser is signed in to the board, and a board sign-in returns to the page asked for;
- have their own identity (`password:<username>`), games, board session and telemetry player ID, never shared with a Google account, even one whose email is the same as the username;
- are never admins;
- get the reserved place at the player cap that the single Google reviewer used to have, at sign-in and on tool calls;
- are revoked (their cookies and tokens refused) when removed from the setting or given a new password, at the next restart.

Wrong usernames and wrong passwords get the same message and take about the same time. Failures are throttled per username (10 per 15 minutes) and per client address (30 per 15 minutes), checked before any password is compared. No password, attempted password or attempted username reaches the logs or telemetry; `sign_in` records now say which provider was used, and refused password attempts are recorded as `sign_in_refused` (reason `credentials` or `throttled`) with no player. A malformed or plain-text setting stops start-up without echoing the value, and the start-up line reports how many password accounts there are, never who.

The old `TCGREPLAY_REVIEWER` setting is retired: if it is still set the playmat logs that it is ignored and starts normally. The board's menu shows a password account's username with the tooltip "Signed in with a reviewer account". The website's sign-in and connecting guides describe the new page, What's new announces it, the privacy page covers reviewer accounts and the login cookie for any sign-in, and the ChatGPT plugin's review test cases, demo script and submission checklist now tell OpenAI's reviewer to sign in with the configured reviewer account.

## Why it matters

OpenAI's plugin review form requires a username and password for a ready-to-use demo account that works without codes or approvals. A Google-only sign-in could not offer that reliably, since Google may challenge a sign-in from an unfamiliar device, so the ChatGPT submission was blocked. Directory reviewers at OpenAI and Anthropic can now be given credentials the operator controls, while players keep signing in with Google to the same account and games. The page's provider list leaves room for more sign-in providers later without reworking either way in.

## Deviations from the plan

- The plan was corrected before work began, after a drift check against the code (most functions had gained a request context in the Grafana observability change, telemetry's `provider` field already existed, and three more places hash accounts into player IDs: daily activity and the board and MCP trace spans). All of them use the account's player key.
- Password account parsing also refuses entries at different bcrypt costs, so an unknown username and a wrong password always take the same time (found by the first goal check).
- The Google nonce and PKCE verifier are set, and a finished sign-in is taken, under the store's lock, so a double-clicked Google button cannot race the callback.
- The client-address source for throttling is logged once at the first password attempt (header name only), so a deploy check can confirm the edge's headers arrive.
- Tests that pinned the old behaviour were updated, not removed: the first redirect going to Google, the observability runbook rows, the busy and session responses, the reviewer review material and the app spec's secrets. Screenshot baselines for the changed website pages were re-recorded.
- The last task, configuring the reviewer accounts on the live playmat and in OpenAI's dashboard, was skipped in this run at the user's decision: it needs the deployed code, the DigitalOcean console and the OpenAI dashboard, and the user will do it after pushing (steps 4 and 5 of `plugin/SUBMITTING.md`, checked by the manual test plan).
- Process: one task's edits first landed in the main checkout because a compound `cd` into the worktree did not persist; they were moved into the worktree and the main checkout restored.
