# tcgreplay now has a public website, and the board has moved to /board

The hosted playmat at https://tcgreplay.demo.gs now opens on a public website instead of going straight to Google sign-in. It has a home page with an animation of the playmat in action, step-by-step guides for connecting it to claude.ai, ChatGPT, Claude Code or the Claude desktop app, a page for every coaching workflow with example prompts, a ready-made example game, the hosted service's limits and a privacy page. The board itself now lives at `/board`. New board links from your assistant point there, but links from older chats open the home page instead.

> Derived from project tcgreplay (spec/plan 20261106110254-f08e142d-project-website). See the project-level record for the full feature.

## What changed in this repo

- **The website (`site/`, new).** A static Astro 7 project:
  - **Shared layout:** logo, navigation, the unofficial fan project notice and the TCGdex credit on every page; system fonts only; no cookies or third-party resources.
  - **Pages:** the home page with the animated playmat scene; the docs pages (connect, sign-in, desktop, import, the coaching workflows, rewind, example game, limits, developers); the privacy page; and a 404 page.
  - **Copy buttons:** every prompt, address, command and the example game.
  - **Build-time checks:** guide/page pairing from `internal/guides` and `guides.go`, the limits from `.do/app.yaml`, and the example decklist from `testdata/decks`.
  - **Browser tests:** a Playwright suite in `site/e2e`.
- **Serving it (`internal/site`, new).** Embeds the built site with `//go:embed`, with a placeholder when it isn't built. `Handler()` serves the pages, `/_astro/` assets with year-long immutable caching, everything else with `no-cache`, and the site's 404 page for unknown paths, never setting a cookie. `internal/site/sitetest/cmd/serve` serves it for the browser suite.
- **Routes (`cmd/tcgreplay/hosted.go`).** The board page is at `GET /board`, behind sign-in and rewritten to `/` for the board server; `/board/` redirects there. `/assets/`, `/ws` and `/api/` stay at the root behind sign-in. Every other path is the website. Board links (`internal/usergames`) are now `/board?board=<handle>`. Sign-in returns to `/board`, and the signed-out, sign-in-problem, "not your game", "not an admin" and admin pages link there (`internal/hostauth`, `internal/usergames`, `internal/cacheadmin`). Tests that pinned the old address were updated, and `TestHostedRoutes` covers the whole path table.
- **The example game.** `site/src/content/example/battle-log.txt` is a corpus game with the opponent's name replaced by "Rival". `internal/game/site_example_test.go` guards it.
- **Build and deploy.**
  - Make targets `site`, `site-dev` and `site-test`; `make test` now also runs the site suite, and `make clean` removes the built site.
  - A `site` stage in the Dockerfile, on `node:22.23.4`.
  - New `.dockerignore` lines.
- **Docs.**
  - The README is now a short introduction linking to the website, with developer notes for the site.
  - The design notes describe the new routes and the site's build.
  - The `.do/app.yaml` header says the site reads the limits from it and that every push redeploys.

## Why

Players needed a page they could open from a shared link to understand the playmat, connect it and start reviewing games; the README only served developers. Serving the site from the playmat itself puts it on the domain Google's OAuth consent screen already trusts. That screen needs a public home page and privacy policy, and this needed no new host, DNS or CI. Reading the guides and limits from the playmat's own files keeps the docs from drifting as the playmat changes.
