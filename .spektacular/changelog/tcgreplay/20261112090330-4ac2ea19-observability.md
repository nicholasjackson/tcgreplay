# Observability: usage and error records keyed by pseudonymous player IDs

The hosted playmat now writes one structured record per line for every
sign-in, tool call, import, new game and error. Players appear only under a
stable pseudonymous ID, never an email. The maintainer can read daily usage
and each player's errors in DigitalOcean Insights. Admins can find a
player's ID from their email on the admin page. Alerts fire on restarts and
on sustained high CPU or memory. Hosted mode now needs a new secret,
`TCGREPLAY_PLAYER_ID_KEY`, to start.

> Derived from project tcgreplay, spec/plan 20261112090330-4ac2ea19-observability. See the project-level record for the full feature.

## What changed in this repo

- **New `internal/telemetry` package**:
  - keyed player IDs (`IDs`, HMAC-SHA256 under `TCGREPLAY_PLAYER_ID_KEY`);
  - the JSON-line `Recorder`, with the closed event catalogue and daily
    `player_day`;
  - `Redact` and `SensitiveFromJSON` for error messages.
- **`cmd/tcgreplay`**:
  - hosted mode reads the key, refuses to start without it, and builds one
    recorder writing to stdout;
  - it adds the tool-call middleware inside the rate limit and wires the
    board error hook;
  - the start-up line says "player IDs on".
- **`internal/hostauth`**: sign-in, refused sign-in, sign-out, rate limit and
  admin refusals are records, no longer email-bearing log lines.
- **`internal/usergames`**:
  - the user cap, expiry, removal and foreign board links are records;
  - `Use` writes `player_day`;
  - new `MCPMiddleware` and `BoardError` record tool calls, imports, new games
    and failures, with redaction drawn from the caller's game.
- **`internal/webui`**: a new `Server.OnError` hook for failed board actions.
- **`internal/cacheadmin`**:
  - admins are named by player ID in log lines and on the page;
  - `admin_action` records;
  - a "Find a player's ID" form (`POST /admin/player`).
- **`.do/app.yaml`**: declares `TCGREPLAY_PLAYER_ID_KEY` (secret) and the
  `RESTART_COUNT`, `CPU_UTILIZATION` and `MEM_UTILIZATION` alert rules. The
  launch limits are unchanged, with comments pointing at the runbook.
- **New runbook, `docs/observability.md`**: the event catalogue, the Insights
  searches, the lookup path, the alerts, capacity (pending measurement) and
  retention (provisional 7 days, to be confirmed).
- **Tests**:
  - unit, component and end-to-end tests for every record;
  - privacy checks covering emails, tokens, log lines and card names;
  - the admin lookup;
  - a source guard against logging an `.Email`;
  - an opt-in memory measurement (`TCGREPLAY_MEASURE_MEMORY=1`).

## Why

A public playmat needs its maintainer to see how it is used and to catch
problems early, without keeping anything that identifies a player. This repo
holds the playmat, so it got the recorder, the ID scheme, the redaction, the
admin lookup and the app definition's alerts.

## Before deploying

Set `TCGREPLAY_PLAYER_ID_KEY` (for example from `openssl rand -base64 48`)
on the live app first. Then apply `.do/app.yaml` with `doctl apps update`
and set the alert recipients in the control panel. The memory measurement,
the launch limits and the confirmed retention periods are the maintainer's
follow-ups (see `docs/observability.md`).
