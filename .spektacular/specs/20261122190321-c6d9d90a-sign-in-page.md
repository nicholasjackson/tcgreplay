# Feature: 20261122190321-c6d9d90a-sign-in-page

## Overview

TCG Replay's hosted playmat gets a sign-in page that offers two ways in: a username and password form for a small set of accounts the operator sets up, and a "Sign in with Google" button for everyone else. It is shown whenever someone connects TCG Replay from an assistant or opens the board in a browser, and one sign-in covers both. This lets directory reviewers at OpenAI and Anthropic test TCG Replay with credentials we give them, without a Google account that Google's security checks could block, while players keep signing in with Google as before. The page is built so other sign-in providers, such as Facebook, can be added later as more buttons.

## Requirements

- [x] **One sign-in page for every sign-in**
  When a sign-in is needed on the hosted playmat, whether an assistant is connecting TCG Replay or a signed-out browser opens the board, the system shows the TCG Replay sign-in page instead of going straight to Google.
- [x] **Google stays available to everyone**
  The sign-in page offers a "Sign in with Google" button, and a player who uses it ends up signed in exactly as they are today, with the same account and games.
- [x] **Username and password for configured accounts**
  When the operator has configured one or more password accounts, the sign-in page shows a username and password form, and entering a configured account's username and password signs the person in as that account.
- [x] **Several configured accounts**
  The operator can configure more than one password account (for example one per directory reviewer), each with its own username and password, and can add or remove one by changing the hosted configuration alone, with no code change or new build. Each signs in as a separate account with its own games.
- [x] **No form without accounts**
  When no password accounts are configured, the sign-in page still appears and shows only the Google button.
- [x] **No password change or recovery**
  Besides having no sign-up (see Constraints), the sign-in page offers no way to change or recover a password, and a short note under the form tells visitors it is for reviewer and invited accounts.
- [x] **One sign-in covers connecting and the board**
  A password sign-in ends the same way a Google sign-in does: when it was started by an assistant connecting, the connection completes; when it was started by opening the board, the browser returns to the page it asked for; and in both cases that browser is then signed in to the board.
- [x] **Failed sign-ins reveal nothing**
  A wrong username or a wrong password gets the same message, so a failure does not reveal whether a username exists.
- [x] **Repeated failures are slowed down**
  The system limits repeated failed password sign-ins, so passwords cannot be guessed by trying many in quick succession.
- [x] **Configured accounts always get a place**
  The hosted playmat accepts a limited number of players holding games at once, and turns new players away when it is full. Today one configured reviewer account is exempt: it can always get in, and it does not use up one of the limited places. Every configured password account gets the same exemption.
- [x] **Password accounts are kept apart from Google accounts**
  A password account never shares an identity, games or board session with any Google account, including one with the same email address or name.
- [x] **Password accounts are not admins**
  A password account never has admin rights; admin access stays limited to verified Google accounts.
- [x] **Credentials never appear in plain text**
  Passwords are never stored or configured in plain text, and neither passwords nor attempted passwords appear in logs or telemetry.
- [x] **Reviewer materials describe the new sign-in**
  The materials prepared for the directory reviews (the TCG Replay plugin's review test cases, demo script and submission checklist) tell the reviewer to sign in with their configured reviewer account instead of a Google account.

## Constraints

- **Only operator-specified accounts.** Username and password sign-in must accept only accounts the operator configures; there must be no sign-up form.
- **Hosted playmat only.** The change applies to the hosted site; the local desktop playmat, which has no sign-in, must stay as it is.
- **Room for more providers.** The page must be able to take further sign-in providers (Facebook and others) later as additional options, without reworking the password or Google sign-in.
- **The assistant connection contract must not change.** Assistants already connected or connecting to TCG Replay (ChatGPT, Claude, MCP Inspector) rely on its existing OAuth flow: client registration, the authorization step, PKCE and tokens. The sign-in page changes only what the person sees during the authorization step, not the protocol.

## Acceptance Criteria

- [x] **Connecting shows the sign-in page**
  When an assistant starts connecting TCG Replay on the hosted playmat (for example from ChatGPT or MCP Inspector), the browser shows the TCG Replay sign-in page rather than Google's.
- [x] **Opening the board signed out shows the sign-in page**
  When a signed-out browser opens a board page on the hosted playmat, it is shown the TCG Replay sign-in page rather than Google's.
- [x] **Google sign-in works as before**
  Choosing "Sign in with Google" on the sign-in page and completing Google's sign-in leaves the player signed in to the same account, with the same games, that they had before this change, both when connecting from an assistant and when opening the board.
- [x] **Configured account signs in**
  With a password account configured, entering its username and password on the sign-in page signs the person in: the assistant's connection completes and its tools work as that account.
- [x] **Two accounts stay separate**
  With two password accounts configured, each signs in successfully with its own username and password, and a game imported by one is not visible to the other.
- [x] **Form hidden with no accounts**
  With no password accounts configured, the sign-in page shows the Google button and no username or password fields.
- [x] **No sign-up or recovery on the page**
  The sign-in page has no link or control for creating an account, changing a password or recovering one, and shows a note that the form is for reviewer and invited accounts.
- [x] **Board opens signed in after connecting**
  After signing in with a password account while connecting from an assistant, opening a board link in that same browser shows the board without asking to sign in again.
- [x] **Board sign-in returns to the page asked for**
  Opening a specific board page while signed out, then signing in with a password account, lands the browser on that same board page.
- [x] **Same message for wrong username and wrong password**
  Signing in with an unknown username and signing in with a known username and a wrong password show the same failure message and do not sign anyone in.
- [x] **Guessing is throttled**
  After at most 10 failed password sign-ins for the same username within 15 minutes, further attempts for that username are refused for a period, even with the correct password, and the page says to try again later; attempts spread across many usernames from one client are throttled as well.
- [x] **Configured accounts get in when the playmat is full**
  With the playmat at its player limit, a configured password account can still sign in and import a game. With the playmat one below its limit, a password account signs in and imports a game, and a new Google player can still join afterwards.
- [x] **No crossover with a Google account of the same name**
  A Google account whose email or name matches a password account's username does not see that password account's games, and the password account does not see the Google account's games. Signing in with one of them in a browser never leaves that browser signed in as the other.
- [x] **Password accounts cannot reach admin pages**
  Signed in with a password account, the admin pages and actions are refused.
- [x] **No plain-text passwords in configuration or logs**
  The hosted configuration holds no password in plain text, and after successful and failed password sign-ins the server's logs and telemetry contain neither the passwords used nor the passwords attempted.
- [x] **Reviewer materials updated**
  The plugin's review test cases, demo script and submission checklist instruct signing in with the configured reviewer account and no longer tell the reviewer to use a Google account.

## Technical Approach

- **Put the page where sign-in starts.** Both the assistant connection and the board's sign-in already start a sign-in at one shared point that goes straight to Google; the page belongs there, so both get it and both finish through the same completion as a Google sign-in.
- **Treat each way in as a provider.** Model Google and password sign-in as interchangeable providers that end in the same signed-in account, so a later Facebook button is one more provider rather than a new flow.
- **Configure accounts like the other hosted secrets.** Keep the account list (usernames and password hashes) in the hosted app's encrypted environment settings, read at start-up, matching how the playmat's other secrets are handled; use a deliberately slow, salted password hash.
- **Reuse the existing reviewer place and rate limiting.** Extend the reserved reviewer place to every configured password account and retire the single reviewer email setting (if it is set in production, move that reviewer to a configured password account first, so the hosted app keeps starting cleanly); throttle failed attempts with the playmat's existing rate-limiting.
- **Give password accounts their own identity space.** Derive a password account's identity so it cannot equal any Google account's, so games and sessions never cross.
- **Known risk: the page is now on every player's path.** Players see an extra click before Google; keep the page light and clear, and make the Google button the obvious choice.

## Success Metrics

- OpenAI's plugin review signs in with the configured reviewer account and runs the test cases without a "reviewers cannot connect" rejection.
- Claude's directory review can be given its own configured account without any code change.
- Players' Google sign-ins keep succeeding after release: Google sign-in completions in the two weeks after release stay at the level of the two weeks before, and no player reports of lost games or accounts.

## Non-Goals

- Sending email of any kind, including magic links and one-time codes.
- Facebook or any sign-in provider other than Google and password accounts; the page only leaves room for them.
- Managing password accounts from a web page; the operator sets them in the hosted configuration.
