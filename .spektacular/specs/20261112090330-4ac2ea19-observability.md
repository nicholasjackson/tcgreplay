# Feature: 20261112090330-4ac2ea19-observability

## Overview

Once TCG Replay is public, the maintainer needs to know how much it is used and to spot and diagnose problems before players report them. The playmat records what players do (each action their AI assistant takes on the playmat, and which assistant took it, plus imports, games and sign-ins) under a pseudonymous player ID, a scrambled stand-in for the email address, and records its own errors. It relies on its hosting platform for traffic, response times and resource use, with alerts when it crashes or runs short of resources. Everything is read in one place, the hosting platform, and nothing in the records identifies a player.

## Requirements

- [x] **Usage is recorded**
  Each tool call (which tool, which assistant), each import, each new game and each sign-in is recorded with the time and the player's pseudonymous ID.
- [x] **The maintainer can read daily usage**
  The maintainer can see, for each day: the number of distinct players, tool calls by assistant, imports and new games.
- [x] **Errors are recorded**
  Every error the playmat hits while serving a player is recorded with the action or tool that failed and the error message, together with the player's pseudonymous ID where there is one.
- [x] **Records never identify a player**
  No record contains an email address (see Constraints), name, Google token, battle log, decklist or card data; players appear only as their pseudonymous ID.
- [x] **Existing log lines switch to the ID**
  The records the playmat already writes on sign-in, sign-out, when a limit stops a request and when a game expires use the pseudonymous ID in place of the email address they carry today.
- [x] **The same player keeps the same ID**
  A player's pseudonymous ID is the same across sign-ins, assistants, restarts and redeploys, and can't be turned back into their email by someone reading the records.
- [x] **The maintainer can find a player's ID**
  When a player reports a problem, the maintainer, and nobody else, can find the pseudonymous ID that belongs to their email address.
- [ ] **Traffic and resources are visible**
  The maintainer can see request rate, response times, responses by status code, CPU, memory and restarts over time.
- [ ] **Alerts for crashes and resources**
  The maintainer is alerted when the playmat restarts unexpectedly, and when its CPU or memory use stays above a threshold the maintainer sets.
- [ ] **Launch capacity is set from measurement**
  How much memory a typical game uses is measured, and the player limit and instance size for launch are set from that measurement, leaving headroom so the playmat doesn't run out of memory at the limit.
- [ ] **How long records are kept is known**
  How long each kind of record (usage, errors, the hosting platform's metrics) is kept is found out and written down, for the privacy page to state.

## Constraints

- Everything is read in DigitalOcean (App Platform Insights, its log viewer and its alerts); no log forwarding service or second monitoring vendor (the maintainer's decision; Sentry and a Cloudflare Worker setup were rejected).
- The playmat runs as a single instance with no database or other persistent storage; recording usage and errors must not add any.
- The privacy page (a separate spec that depends on this one) must be able to describe everything recorded here and how long it is kept.
- The pseudonymous ID is a one-way hash of the player's email address, and no email address appears anywhere in the logs (the maintainer's decision).
- The hash is keyed with a secret kept out of the code and the logs and unchanged across restarts and redeploys, so that hashing a list of known emails can't match records; changing the secret changes every player's ID.
- The maintainer-only lookup uses the playmat's existing Google sign-in and its existing admin list.

## Acceptance Criteria

- [ ] **Usage records appear**
  After a player signs in, imports a battle log through an assistant and starts a game, the hosting platform's log viewer shows a record for each sign-in, tool call (naming the tool and the assistant), import and new game, each with a time and the same pseudonymous ID.
- [ ] **Daily usage readable**
  On a day when player A uses the playmat twice and player B once, the maintainer can read a distinct-player count of 2 for that day, and its tool calls by assistant, imports and new games, in the hosting platform without any other service.
- [x] **Errors recorded with context**
  When a tool call fails (for example an import of a malformed battle log), a record shows the tool that failed, the error message and the player's pseudonymous ID.
- [x] **No identifying data**
  Searching a day's records for the test players' email addresses and Google display names, a Google token value, a pasted battle log's text and a deck's card names finds nothing.
- [x] **Existing log lines use the ID**
  Signing in, signing out, hitting a use limit and letting a game expire each write a record with the pseudonymous ID and without the email address.
- [x] **Stable, one-way ID**
  The same account gets the same ID before and after a sign-out, a different assistant and a redeploy; two accounts get different IDs; and hashing the test player's email without the playmat's secret does not produce their ID.
- [x] **Maintainer-only lookup**
  Signed in as an admin, the maintainer can enter a player's email and get their pseudonymous ID; a signed-in non-admin, or anyone signed out, can't.
- [ ] **Graphs available**
  The hosting platform's dashboard shows request rate, response time, responses by status code, CPU, memory and restart count for the playmat over the last 24 hours and the last 7 days.
- [ ] **Alerts reach the maintainer**
  An alert reaches the maintainer when the playmat restarts unexpectedly, and a CPU or memory alert reaches them when its threshold is temporarily lowered below current use.
- [ ] **Capacity measured and set**
  The project records the measured memory use of a typical game (a full imported game with branches) and the launch player limit and instance size chosen from it; with that many games open, memory use stays below the instance's limit with headroom to spare.
- [ ] **Retention written down**
  The project records how long usage records, error records and the hosting platform's metrics are each kept.

## Technical Approach

- Prefer structured (one JSON object per line) records with a fixed event name and fields, so the log viewer can filter them and the daily numbers can be read from them.
- For daily usage, prefer numbers worked out from the individual records in the log viewer; a running count held in the playmat's memory would be lost on every restart or redeploy, so a daily summary record or admin-page counts would undercount unless they account for that.
- Prefer App Platform's own alert rules (restart count, CPU, memory), sent to the maintainer's email.

## Success Metrics

- A week after launch, the maintainer can say how many distinct players used the playmat each day and which assistants they used, from DigitalOcean alone.
- When a player reports a problem, the maintainer can find the matching error records from the player's email in under five minutes.
- No crash or resource exhaustion in the first month goes unnoticed until a player reports it.

## Non-Goals

- The privacy page's wording: the privacy, terms and disclaimer spec.
- Visitor analytics for the website and board pages: the visitor-analytics spec.
- Alerts for failed deploys or domain and certificate problems.
- Public usage numbers or a stats page.
