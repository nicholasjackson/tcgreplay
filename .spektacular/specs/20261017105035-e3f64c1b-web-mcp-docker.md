## Overview

Host the playmat at a public web address, so Claude in claude.ai (web or mobile) can connect to it and play out and analyse a game on the board without the player's desktop. Whenever Claude opens or creates a game, it gives the player a link that opens the live board in their own browser tab and follows along as Claude acts. This first step is a short, open trial for the owner alone that proves claude.ai can drive the hosted board before sign-in and separate games for each user are added, while today's desktop setup keeps working exactly as before.

## Requirements

- [ ] **Remote connector**
  A user can add the hosted playmat to claude.ai as a custom connector by its web address, and claude.ai lists the same playmat tools the desktop setup offers.
- [x] **Full tool parity**
  Every playmat tool available on the desktop works the same way through the hosted connector: importing a log, setting the opponent's deck, moving cards, rewinding, branching and annotating.
- [x] **Board link**
  Whenever a tool opens or creates a game (import, new game, load game), its result includes a link the user can open in a browser to see that game's board.
- [x] **Live board**
  The board opened from the link shows the current game and updates as Claude acts, with no manual refresh.
- [x] **Board interaction**
  The user can act on the board from the browser tab, as they can on the desktop, and Claude sees those changes.
- [x] **One address**
  The connector and the board are both reached through the same public address.
- [x] **Configurable public address**
  The operator can tell the playmat the public address it is reached at, and board links use that address.
- [x] **Container deployment**
  The operator can start the hosted playmat with one command and configure it through settings, not code changes.
- [ ] **Push to deploy**
  Publishing a code change deploys the hosted playmat with no manual steps.
- [x] **Card data when hosted**
  Card text and images are available in the hosted playmat without any setup beyond starting the container.
- [x] **Desktop unaffected**
  The existing desktop setup (Claude Desktop and Claude Code launching the playmat locally) behaves exactly as before.

## Constraints

- Must be a mode of the existing tcgreplay binary, not a separate program; the desktop modes (stdio MCP, shared daemon and shim) must remain.
- Must run as a Docker container.
- Must run as a single instance.
- Must serve plain HTTP on the port the hosting platform assigns. HTTPS is provided in front of it (App Platform, with Cloudflare in front of the owner's domain), and the container does no TLS of its own.
- Must deploy to DigitalOcean App Platform, built and deployed automatically when changes are pushed to the `main` branch of the GitHub repo; pushes to other branches do not deploy.
- Must work as a claude.ai custom connector, meeting claude.ai's requirements for remote MCP servers.

## Acceptance Criteria

- [ ] **Connector connects**
  With the container running behind its public HTTPS address, adding that address as a custom connector in claude.ai succeeds, and the connector's tool list in claude.ai matches the tools the desktop setup lists.
- [ ] **Import and play through the connector**
  In a claude.ai conversation, Claude imports a real TCG Live battle log with an opponent deck, moves a card, rewinds, makes a branch and adds an annotation. Each call returns a success result, and reading the state back shows each change.
- [x] **Every tool works hosted**
  The existing automated tool tests pass when run through the hosted connection, not just the desktop one.
- [x] **Link in results**
  The results of import, new game and load game each contain a board link that starts with the configured public address.
- [ ] **Link opens the right board**
  Opening that link in a browser on another device (e.g. a phone) shows the board of the game the tool just opened.
- [ ] **Board follows Claude**
  With the board open, a move Claude makes through the connector appears on the board within 2 seconds, with no page reload.
- [ ] **Board stays connected**
  Left open and idle for 10 minutes behind the Cloudflare proxy, the board still shows Claude's next move without a reload.
- [x] **User moves reach Claude**
  A card the user moves on the hosted board appears in the state Claude reads back through the connector.
- [x] **Single address**
  The connector address and the board links share the same host, and no other port or host is needed to use either.
- [x] **Public address setting**
  Changing the public address setting and restarting the container changes the address used in board links, with no rebuild.
- [x] **One-command run**
  The container image builds from the repo with one command and starts with one command plus settings, and the board loads at its address.
- [ ] **Push deploys**
  After a push to `main`, App Platform builds the new version, and the connector and board serve it without anyone touching the server.
- [ ] **Card data out of the box**
  In a freshly started container, the card text tool returns text for a card in the imported game, and the board shows that card's image.
- [ ] **Desktop regression**
  After the change, the existing automated tests pass, and the desktop setup (Claude Code and Claude Desktop launching the playmat locally) connects and imports a log as before.

## Technical Approach

- Prefer the official Go MCP library's web transport for the connector, served from the same web server as the board so one address covers both.
- Board links use the configured public address because the incoming request's host can't be trusted behind Cloudflare.
- Prefer one container image that builds both the board UI and the binary, so the image is self-contained.
- Prefer keeping App Platform's app definition in the repo, so the deployment can be reproduced and is reviewed alongside the code.
- For this trial, writing game files and the card cache to the container's own filesystem is acceptable, since it disappears with the container.
- Prefer to keep TCGdex as the card data source, fetched at runtime by the running container.
- Risk: every deploy replaces the running container, so a game in progress is lost and must be re-imported (see Non-Goals: no keeping games across restarts or deploys).
- Risk: Cloudflare drops idle connections after about 100 seconds. The board's live connection and any long-running connector responses may need keep-alive messages or short-lived replies.
- Risk: claude.ai's requirements for connectors without login aren't confirmed. Check them first, because if claude.ai won't connect, nothing else in the epic works.

- Deploying a change takes nothing beyond a `git push`, with no manual steps on DigitalOcean.
- This trial gives a clear go/no-go answer for the rest of the epic: either claude.ai can drive the hosted board, or we know exactly what blocks it.

## Non-Goals

- No login or access control. The trial is open and short-lived; Google login comes in the google-login spec.
- No in-memory-only storage, no tool that hands the game record back to Claude, and no way to replay an import exactly from a saved record; those come in the memory-store-record spec.
- No separate games per user. Everyone who reaches the server shares one game, as on the desktop today; that comes in the per-user-games spec.
- No packaging of the tcg-* skills for claude.ai; that is a later spec, and this one only proves the tools work.
- No Notion integration.
- No board inside the Claude chat (MCP Apps), and no chat inside the board page; the board opens in its own tab.
- No keeping games across restarts or deploys.
